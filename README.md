# 记账

把支付宝、微信、银行导出的账单文件导进来，自动记录成结构化的收支。
本地 Web 应用，数据存在本机 SQLite 里，文件不出这台机器。

界面就四个 tab：**汇总**（首页 dashboard）、交易记录、导入账单、设置。

## 跑起来

```bash
uv sync          # Python 那半边（flask + openpyxl）
./deploy.sh      # 构建前端产物，装到 src/bill/static/app/
uv run bill
```

默认监听 `0.0.0.0:8001`（所有网卡）。本机开 <http://127.0.0.1:8001>，
从别的机器就用这台机器的 IP，例如 <http://10.0.0.5:8001>。

**前端产物不进版本库**，所以第一次跑之前要构建一次（`deploy.sh` 会做，它构建到
旁边的目录、成了再换上去，并留着上一份）。产物不在时页面会明确说「前端还没有
构建」而不是白屏。

改界面的时候用 `npm --prefix frontend run dev`（Vite 起在 5173，把 `/api` 转给
8001 那个 Flask）；改完照旧走 `./deploy.sh`。

## 登录

```bash
uv run bill --set-password                    # 交互式：先问账号，再问两遍密码
uv run bill --set-password --user 账本主人     # 账号直接给，只问密码
echo '……' | uv run bill --set-password --user 账本主人  # 脚本 / 管道里这么给
```

登录要**账号加密码**两样，但**只有一组凭据**：账号名不是用来区分人的（账本只有
一份，也不记「这笔是谁记的」），它是「对得上就进」的那道门的一部分。账号名回车就
沿用现有的，没设过就是 `bill`——这一条是为了**升级上来的人**：加账号之前写的
`auth.toml` 里只有密码，那份配置读出来按 `bill` 算，不然升级完打开页面，得先猜中
一个谁也没告诉过他的账号名。想换成别的，跑一次 `--set-password` 就行。

设完之后**每个接口**都要先过这道门（问「我登没登」、登录、退出这三个除外），
**改完不用重启**——跟设置一样每次请求现读。密码存在
`~/.local/share/bill/auth.toml`，里面是 scrypt 加盐哈希，不是明文；账号名是明文
（它本来就要在登录页上打出来）；会话密钥也在那份文件里，所以重启服务不会把你从
浏览器里踢出去。只改密码不会动账号名，也不会动会话密钥。

登录这一步**在界面里完成，不跳页**：外壳（那个 SPA 的 HTML）本身不含任何账目数据，
数据全在 `/api/*`。所以没登录时打开首页看到的是应用壳加一个登录框，登完还留在原来
那个地址上。接口那一侧没登录一律回 401 加一句中文，不跳转——把一个 303 交给
`fetch`，跟着拿回来的是一整页 HTML，屏幕上就是白屏而不是登录框。

口径上还有一条：改状态的接口只收 `Content-Type: application/json`。跨站的
`<form>` 发不出这个类型，所以这一条又堵掉一条路（会话 cookie 本身是 `SameSite=Lax`，
跨站提交本来就带不上它）。没有引入 CSRF token——单人本地应用，收益不抵复杂度。

**没设密码 = 不设防**，跟以前一样谁都能看。这种状态会在每个页面顶上挂一条提示，
不会悄没声地过去；要主动关掉登录，把 `auth.toml` 删掉即可。

一个账号、一个人，没有多用户也没有「找回密码」——忘了就再跑一次 `--set-password`，
旧的当场作废。账号错和密码错回**同一句**「账号或密码不对。」：分开说等于告诉猜的人
「账号对了、接着猜密码」。同一个来源连错 5 次会歇 60 秒；**歇的是「猜」，不是人**——
这段时间里输对凭据照样进得来（一个人用的账本只有这一组凭据，被别人拿错的凭据堵在
门外比被多猜几次糟得多）。计数在内存里，重启服务就清零。

> ⚠️ 走的是明文 HTTP：密码和会话 cookie 在有嗅探的网络上都是明摆着的。这道防线
> 挡的是「能连上 8001 端口的人」里那些顺手点进来的人，不是网线那头的人。真要隔着
> 不受信任的网络用，还是靠防火墙兜住，或者 `HOST=127.0.0.1` + SSH 隧道。

`HOST` / `PORT` 可以覆盖监听地址，`FLASK_DEBUG=1` 开调试模式。

## 设置页

下面那些 `.toml` 里的东西，绝大部分在「设置」页上就能改：配色、显示币种与汇率、
时区、大额阈值、合并的几个参数、导入提醒的天数。保存写的是你自己的那份配置
（`~/.local/share/bill/settings.toml`），**整份重写**；写之前会把原来的内容留一份
`settings.toml.bak`（只留一次，不会被后来的保存顶掉）。手改文件仍然照旧有效。

### 配色

四套，在设置页上点一下即换：

| 名字 | 说明 |
| --- | --- |
| `dark` | 深色（默认） |
| `light` | 浅色 |
| `dark-teal` | 深色 · 青橙 |
| `light-teal` | 浅色 · 青橙 |

四套各有自己的收入 / 支出色。这两色**同时**是表格里那些数字的颜色和图表里柱子的
颜色，所以挑的时候有两个约束，缺一不可：

- **分得开**。红绿色盲下的 OKLab 色差 ≥ 8（四套分别是 19.2 / 20.3 / 10.1 / 9.4）。
- **读得清**。当正文用，对各自的表面 ≥ 4.5:1。原来那对绿 / 红是 2.1，等于红绿色盲
  完全分不出收入和支出。

**配色的取值只有一个地方**：`frontend/src/theme/theme.json`。每个主题的
`:root[data-theme=…]` 变量块和图表用的颜色都从它出来（变量块由
`frontend/scripts/gen-themes.mjs` 生成），所以「两处颜色不一致」在构造上不可能发生。
哪些主题存在、各自叫什么，由 `src/bill/themes.py` 说——`settings.toml` 里写错一个
配色名要当场报出来，而那道校验不该去读前端的一个数据文件；标签也从那边出。
两边对不上时 `tests/test_theme_sources.py` 会挂。
那两条质量线钉在 `frontend/src/theme/theme.test.ts` 里，换新配色时先要过它们。

### 界面里不写实现说明

一个约定：**页面上只放数据、控件和必要的警告**，不写「金额已按 1 GBP = 8.9 CNY
换算」「时间均已换算到 Europe/London」这类说明，也不写「为什么这样设计」的辩解。
它们读起来像提交说明，而且真正要在意的人看这一页就够了。口径（阈值多少、汇率多少、
窗口多长）在设置页上是**控件本身**，不在页面顶部另起一段话。
`tests/test_settings.py` 里有条用例拦着这件事。

## 支持的账单

| 来源 | 格式 | 说明 |
| --- | --- | --- |
| 支付宝 | 明细 CSV（GBK 编码），或包含它的 ZIP | 前面有账户说明、末尾有汇总，都会自动跳过 |
| 微信 | 账单 XLSX | 金额是纯数字，`/` 表示不计收支 |
| Monzo | 导出 CSV | 日期和时间分两列，金额带正负号，币种是英镑 |
| 中国银行 | 交易流水明细 PDF（文字版） | 密码就是文件名去掉 `.pdf`；每页重复表头自动合并；扫描件不支持 |
| 银行 | CSV / XLSX / PDF，**列映射可配置** | 见下面「加一家银行」 |

拿到新的账单文件直接传上去就行。认不出格式时预览页会把文件开头的**原始内容**摊出来，
并指到列映射那一页——那儿列着刚读到的**真实表头**，照着改配置即可。

## 币种与汇率

账本里可以同时有人民币、美元和英镑（比如微信 + Monzo + 中国银行）。所有金额都按
汇率**换算成同一种币种**显示和统计，默认是英镑：

```toml
# ~/.local/share/bill/settings.toml
[currency]
display = "GBP"
rates = { CNY = 8.9 }     # 1 GBP = 8.9 CNY，也就是人民币金额 ÷ 8.9 = 英镑金额
```

改完刷新页面就生效，不用重启。这几项在**设置页**上就能改；想手改文件的话，内置的
那份在 `src/bill/data/settings.toml`，复制到上面的路径就行。

**设置页会把账本里出现过的币种和笔数自动列出来。** 还没配汇率的币种带着「未配
汇率」标记和笔数，在那里填上数就立即并进显示币种，不用先知道账本里有哪几种钱。
汇率的方向是「1 单位显示币种 = 多少该币种」。

**没配汇率的币种不会被合并。** 它们仍按原币种单独成组，首页会写「USD 5 笔还没配
汇率」并给一个去设置页的入口。把没有汇率的币种按 1:1 混进合计会得到一个不报错的
错数——那比报错危险得多，所以宁可多一个提示，也不写那句话去解释。

界面上以**换算后的金额为主**，账单上的原币金额用小字跟在旁边；详情页的「原金额」
明细一直保留原币。原始金额和币种也一直留在库里（`amount_cents` / `currency`），
换算是查询时做的，所以改汇率随时可以重算，不会把历史数据改坏。金额一律存整数
最小单位（人民币的「分」、英镑的便士），跟币种无关。

**不做历史汇率**：用的是你现在设的这一个数，不是每笔交易发生当天的汇率。

有些账单不写 `GBP` / `CNY`，而是写「英镑 / 人民币 / 美元」。配置里的
`[values.currency]` 负责把它们映射成 ISO 代码；没映射上的写法会按原样大写，
不会悄悄当成显示币种。

## 时区

账单给的时间都是**当地的墙上时钟**，不带偏移量，而且各来源还不一样：

| 来源 | 时间是哪个时区的 |
| --- | --- |
| 微信 / 支付宝 | UTC+8（微信账单第一页自己就这么写着） |
| 中国银行 | UTC+8（北京时间） |
| Monzo | 英国本地时间（会随夏令时变） |

账本统一换算到一个显示时区，默认英国：

```toml
# ~/.local/share/bill/settings.toml
timezone = "Europe/London"   # 必须写在文件最上面，不能写在 [currency] 之后
```

换算在**导入时**做一次，原始的那串时间一直留在 `raw_json` 里随时能对回去。

不换算会怎样：北京时间 `11-01 02:00` 的一笔，按英国时间其实是 `10-31 18:00`，
不换算就会被算进 11 月——**而这不会报任何错**。同理，一天之内两种来源的先后顺序
也会错位。

用的必须是 IANA 名字（`Europe/London`）而不是固定偏移量，因为英国一年里会
夏令时切换两次；写错名字会在读设置时就报错，不会拖到导入。（设置页上那一格同理，
填错了当场告诉你。）

自己加的银行配置默认**不换算**（当作已经是显示时区）；只有当那份账单来自别的
时区时，才需要在 `[profile].timezone` 里声明。

## 大额交易

买台 iPad 的 −£1000、或者爸爸给的 +£5000，混在日常收支里会把「累计支出」「累计收入」
抬到一个不反映真实水平的数。所以超过阈值的单笔**不进合计**，但仍**照常留在账本里**，
在汇总页最底部单独列一块（标题里带着条数）。

```toml
# ~/.local/share/bill/settings.toml
[large]
out = 500     # 单笔支出 ≥ 500 就算大额
in  = 2000    # 单笔收入 ≥ 2000 才算；0 表示这一侧不启用
```

这两项在设置页上直接填，改完点保存即可。

阈值是**显示币种的主单位**，不是人民币，也不是英镑——跟着 `[currency] display` 走。
所以同一个「500」在 GBP 账本下是 £500，在 CNY 账本下就是 ¥500。**人民币账本下这两个
默认值多半要往上调**：¥2,000 只相当于约 £225，一笔正常工资就会被当成大额剔掉。

只对**换算得到显示币种**的记录生效。没配汇率的币种比不了（拿英镑的阈值去比人民币的
数没有意义），所以那几组里一笔都不会被判成大额——跟「没配汇率就不合并」是同一个
道理，都是宁可少做也不给一个不报错的错数。

判断是**查询时**做的，跟汇率换算一样：改完阈值刷新页面就重算，库里不加列、不改数据。
今天觉得 £1000 算大额，明年想改成 £1500，改个数就行，历史数据不会被动过。

几处刻意的选择：

- **收入和支出分开两个阈值，而且默认都开着**。两者尺度本来就不同，共用一个数会让
  收入那一侧形同虚设（工资通常就超过一般的支出阈值）。但收入侧默认开着是有代价的：
  **月薪一旦超过 `in`，就会被整个剔出「累计收入」**。所以汇总页底部那一块带着条数
  （「不计入合计的大额（2 笔）」），设置页上那两个数就是当前生效的阈值——数字可以
  被改小，但不该是悄悄被改小的。发现剔错了，把 `in` 调大，或者写 `0` 关掉那一侧。
  刻意**不**在合计数旁边再写一段话解释它：那一段话既长又像变更说明，而需要它的人
  看设置页就够了。真觉得对不上账时，数一数底部那几笔的条数。
- **条数照实计数**，不跟着剔除。大额行确实在账本里，只是不参与金额合计——中性行
  早就是这个待遇了。所以「记录条数」减去「金额合计覆盖的条数」是正常的。
- **交易记录页上它们在金额旁标一个「大额」标签**，金额照原样显示。抹成 0 反而更糟：
  那一笔确实发生了，页面上却写成没发生。列表页那一行里没有「计入合计」这一列，
  这个标签就是唯一的交代。
- **导入预览页不套阈值**。那两格是「新增收入/支出」，回答的是「这次写进去多少」，
  不是「账本合计多少」。
- **不分页也不截断**汇总页的那份清单。大额本来就是稀有事件，截断反而会造出「说明里
  写着 N 笔、列表里只有几笔」这种对不上账的情形。真把阈值设得极低，那长长的列表
  本身也是明摆着的。

## 汇总页（首页）

首页是一块 dashboard，回答「最近花得怎么样」。所有数字都用**设置里的显示币种**，
没有币种切换按钮；预测、平均、趋势、排行也只算这一个币种——把人民币和英镑加进
同一张卡，正是这一页处处在避免的错。没配汇率的币种不会混进来，页面上会写
「USD 5 笔还没配汇率」并链到设置页。

**区间**在顶上，左右两个按钮（手机上也可以直接横向滑动）切换月份。默认是**本月
1 号到今天**；翻到某个月就是那一整月。「按月 / 按年」是**区间粒度**，「回到本月」
是一次跳转——两者不是并排的三选一，所以「回到本月」只在离开当前区间时出现。

- **四个数**：本期支出、收入、结余、日均支出。支出和收入整格可点，落到同一段
  区间的交易记录；当前区间没过完时，支出那一格还会跟**上个月/去年同期同一天**比
  ——「1–18 日」跟「上月整月」比会凭空显得花得少。支出、收入、日均支出三格和
  日期栏的背景各有一条很淡的走势线（支出红、收入蓝），日均那一格还多一条虚线
  表示这一段日均。具体数仍然以正文为准，线只是背景。
- **预测与平均**：预计本月/本年支出，按今年/本月到今天的日均外推；月均支出看
  最近 12 个**完整**月，账本不够 12 个月就按实际月份数平均，年均按同一窗口折算。
  大额和中性行不进这些数，跟合计同一个口径。
- **支出趋势**：一个月按天、一年按月，可在**柱状 / 折线**之间切换。当前区间只画到
  今天——后面的日子不是「花了 0」，是「还没到」。
- **花费排行**：分类和单次两个榜，默认各露 5 条，「更多」展开。分类榜还能切成
  **饼图**看构成，扇区和图例同样能点。每一行都点得进去：分类落到交易记录里
  **同一段区间 + 同一个分类**的筛选结果，单次落到那一笔详情（合并组落到合并组页）。
  排行跟合计同口径，也剔除了大额。
- **账户支出构成**（环形）和**不计入合计的大额**在排行下面。前者回答「这个月主要
  是哪张卡在花」，后者是「钱确实花了、但没进上面合计」的那几笔，点得进详情。
- 大额和中性记录各留一句灰字，说明它们没进合计；中性那笔带入口去交易记录逐笔看。
- 从排行、KPI 或大额点进交易记录/详情后，页顶有「← 汇总」，筛选条件已经带上；
  返回时回到同一段区间。

几处刻意的选择：

- **趋势图只有支出一个序列**，所以只有一种颜色、不需要图例——标题已经说了画的是
  支出。柱状看「哪天/哪个月花得多」，折线看整体走势。
- **排行默认用一列很淡的长度条**：长度是最容易比较的编码，金额和占比仍然以文字
  给出。分类榜另给一个饼图切换——分类少时看「谁占大头」更直观；多了就用列表，
  饼图会把小扇区挤成一条缝。
- **分类饼图的颜色按这一段的排名分配**。这一页一次只看一段区间，饼图回答的是
  「这一段里谁占大头」，不需要跨区间认色。扇区之间留一道底色缝隙，不靠颜色也能
  看出边界。
- **账户用环形图**：账户通常只有两三个，适合看「部分占整体多少」。颜色跟着
  **账户本身**走，不跟当前排名走——换一个区间、某个账户这月没花钱，别的账户的
  颜色不会重排。
- **配色跟着主题走**，四套主题各有自己的收入 / 支出色（见「设置页 · 配色」）。
  这几个色都跑过色盲校验，也都能当正文颜色用。
  **配色只有一个来源**：`frontend/src/theme/theme.json`。CSS 变量块由它生成，
  图表组件也直接读它——于是「两处颜色不一致」在构造上不可能发生。
  那两条质量线（色差、对比度）仍钉在 `frontend/src/theme/theme.test.ts` 里，
  换新配色时首先要过的是它们。
- 手机上图表**横向不溢出**：`ResponsiveContainer` 跟着卡片宽度走，日期刻度会自动
  稀疏到放得下为止。

## 导入提醒与账户构成

超过设置里的天数没导入的账户，汇总页上方会有一行提醒；从没导入过的账户写「从未
导入」，同样算进提醒。账户花销本身在首页的「账户支出构成」环形图里——按账户分，
只算当前币种。

```toml
# ~/.local/share/bill/settings.toml
[imports]
stale_days = 30   # 超过这么多天没导入就提醒；0 = 不提醒
```

几处刻意的选择：

- **提醒跟当前选的区间无关**。账户多久没导入是账户自己的状态，不是这段账的特征；
  放进「这个区间里没有记录」那个空状态里的话，当月没记账的人反而看不到该导账单了。
- **「上次导入」用的是导入动作发生的时间**（`imports.uploaded_at`），不是账单覆盖
  到哪一天。删掉一次导入之后，它会回退到上一次。
- **账户构成跟随区间，用设置里的显示币种**。没配汇率的币种不混进来，首页提示里
  会单独说；金额走的是和总计同一份合并后净额，合并组不会被算两遍。
- **0 关掉的是提醒**，账户支出构成照常显示。

## 导入流程

传文件 → **预览确认** → 入库。预览这一步是关键：

- 认成了哪份配置、匹配度多少，可以手动改选并**就地重新解析，不用重传文件**
- 会新增几条、有几条跟库里重复、有几条是中性收支、其中几条会直接隐藏、几条解析不了
- 解析出问题的行会连同**原始内容**列出来，方便你拿去改配置
- **确认之前不会写进账本**，所以格式认错了也不会污染数据

预览只存在内存里，进程重启或放置超过 30 分钟会失效（已入库的数据不受影响）。

## 收支的三个方向

不是「收入 / 支出」两个，而是三个：

- `收入`、`支出` —— 计入合计
- `中性` —— 支付宝的「不计收支」、微信的「/」。转账、还款、退款都归这里；
  银行流水里的「转给自己另一张卡」「购汇」也靠配置里的对方/交易名称规则归到这里

中性行**照常入库**（金额留着、列表里看得见），但不计入任何收支合计。
数据库里用一个视图把这件事固化下来，所以统计查询不可能「忘了排除中性行」。

汇总页上它们**只剩一行灰字**（「另有 N 笔中性记录未计入合计」，带个入口点进交易记录
逐笔看，那一页也能按「中性」筛）。早先它们在汇总页上是一块独立的表（条数 + 金额
合计），跟收入、支出、结余并排——那等于把「不计收支」的东西也摆成一张账，读起来像
「有一块账没算进去」。收入、支出、结余三个数里没有它们，才是这件事的全部意思：
把「转给自己另一张卡」算成支出，等于凭空造出一笔消费。

银行流水常常只有内部转账的**一边**（另一张卡的流水没导），自动合并配不上另一半；
内置的中国银行配置按 `[parse].neutral_counterparties`（对方是本人）和
`neutral_descriptions`（退款）直接判中性。

支付宝还多走一步：「不计收支」的行导入时**直接标记为隐藏**（由列映射里的
`[values].hidden` 点名）。它们仍然入库、仍参与去重，在交易记录页选「只看隐藏」
就能找回来；只是默认视图里灰着，不会混在日常流水里，汇总页也不会再为它们
单独提一句。隐藏和中性不冲突：中性管「算不算钱」，隐藏管「默不默认露脸」。

按月收益汇总**不受自动隐藏影响**：余额宝那类每日收益虽然藏起来了，仍然会按
自然月合成一条收入。汇总取的是中性行，配置自动藏起来的不筛掉——否则开启
汇总之后，这些收益会从月度收入里悄无声息地消失。你手动藏掉的一笔不在此列，
不会被下次扫描又合回来。

## 重复导入不会翻倍

记账是长期的，账户区间重叠是常态——这个月导了 1/1–1/31，下个月导 1/15–2/28，
中间两周是重合的。去重就是为这件事做的。

分两层：

1. **唯一订单号**：支付宝的「交易订单号」、微信的「交易单号」，有就用它。最可靠。
2. **内容指纹**：没有订单号时（多数银行流水），对「时间 + 方向 + 金额 + 对方」取哈希。

内容指纹**刻意不含摘要和备注**。不少银行每次导出都会把日期、网点拼进摘要
（`消费` 变成 `消费 某超市 2026-01-10`），把它们算进指纹的话，同一笔钱在区间重叠的
两次导出里就成了两笔，长期按月导会越滚越多。备注本来就给人改的，同理。

指纹里含**方向**。所以「哪些算内部转账、哪些算退款」这类规则要在第一次确认前定好；
导进来之后再改规则重导同一份文件，被改判的行会被当成新记录。

兜底的两道保险：

- 区间跟历史导入有重叠时，预览页会**明说**跟哪一次重叠了。
- 去重键认不出来、但账本里已有「同一天 + 同方向 + 同金额」的记录时，标成
  **疑似重复**并列出来让你过目。这种情况多半是连对方名都被改写了。

有一处刻意做得不那么「聪明」：**同一份文件里出现两笔一模一样的消费，会被当成两笔真交易
都保留下来**（第二条带个 `#2` 后缀），而不是合并成一条。同一分钟内买两次一样的东西是
真实存在的，静默合并比多存一条糟得多。同理，退款行复用了原订单号也不会被吞掉。

去重按**账户**隔离。同一笔钱从支付宝和从银行流水各导一次不会被自动合并——那属于对账问题，
靠弱内容匹配去自动合并风险更大。

「疑似重复」的行**照常导入**，不自动丢弃：丢真账的代价比多一条大，判断留给你。

## 分类体系

账单来自两套分类：支付宝的「交易分类」（中文，20 多类，最细）和 Monzo 的
Category（英文，官方 API 只有 10 类左右）。账本统一成**支付宝那一套中文分类**：
Monzo 的 `Groceries`、`Eating out`、`Finances` 等会归到「日用百货」「餐饮美食」
「投资理财」，于是汇总页、筛选下拉和列表里不会再出现两行同类开销。

映射表在 `src/bill/categories.py` 的 `_ALIASES`，**只影响显示**：

- `source_category` 里的账单原文一个字都不改，详情页仍能看到 `Groceries`；
- 手改的分类仍然优先生效，只是手改里写的英文别名也走同一张表归一；
- 规则改了刷新页面就重算，不用重导历史数据。

认不出的分类保留原文，不做关键词猜测——归类错一笔和算错一笔没有区别。
emoji 那一层仍有关键词兜底，那只是图标，不参与合计。

## 手改与手动记账

导入只是起点，账总有要动手的地方。交易记录页上：

- 每行末尾的「操作」列上有「改 / 隐藏 / 删」，页头有「记一笔」（临时用现金付的、
  别人代付的都靠它）
- 勾选几笔，可以**一起改分类**，也可以**合并成一组**（见下一节）

几处刻意的选择：

- **手动记的一笔不属于任何账单文件。** 它 `import_id` 留空，落在单独的「手动记账」
  账户里，去重键是个随机值。所以它不参与账单去重——同一天手滑提交两次就是两条，
  跟真买了两次一样。理由和「同一份文件里两笔一模一样的消费都保留」是同一条：
  静默吞掉一笔真账，比多存一条糟得多。
- **手改的分类不会盖掉账单原文。** 账单自带的分类（支付宝的「交易分类」、Monzo 的
  Category）留在 `source_category`，你改的写在另一列 `category`，没改过就回落到
  原文。所以改错了、想对回原样都还有得对，跟「原始金额和币种一直留在库里」一个道理。
- **编辑绝不重算去重键和内容指纹。** 这是全项目最容易踩、踩了还不报错的一处：
  那两个字段是「这条记录的身份」，重算之后重新导入同一份账单时比不中指纹，
  同一笔钱会被**再插一遍**——账翻倍，屏幕上什么都不说。所以账户、来源分类、
  订单号这些也一律不给改：要改分类，改的是上面那个 `category`。
- **改一笔不影响它所在的合并组**——手动合的是你自己勾的，自动合的被改了金额/方向/
  币种/时间会散开（见下一节）。
- **秒不会被悄悄抹掉。** 表单里的时间精确到秒，点一次保存改的是你动过的那部分；
  只到分钟的话，改个备注就把账单里的秒数改了。
- 手机上勾选之后操作条在表格下面，**没有「全选本页」**：批量操作那一块不带 JS，
  与其写一半的交互，不如让人手勾。

### 「隐藏」不是删除

删了就没了；隐藏是把这一笔从账本的口径里摘出去，随时能还原。所以：

- **隐藏之后它不进任何合计**——汇总、图表、大额、币种清单里都没有它。库里那一行
  照旧在，原始金额、币种、去重键、内容指纹一个字不动，**所以重新导入同一份账单也
  不会又插一遍**（跟编辑一样，去重那块的东西谁都别碰）。
- **交易记录页上它照旧列出来，灰字**，勾选列里挂着「隐」，末尾的「操作」列里是「显示」，
  点一下还原。金额照原样写着，不抹成 0——那一笔确实花出去了，页面上写成 0
  才是假数；跟大额一样，靠标记交代它不算数。
- **它连勾选框都没有。** 它不进合计，也就不该能被合进一组。想只挑出这些行，筛选栏
  里有一档「已隐藏」。
- **隐藏不盖「已改」那枚标签。** 那个标签说的是分类手改过；隐藏改的是算不算数，
  跟内容改没改是两件事，混用一个标记会让人以为记录被改过。
- **按「隐藏」不会重载整页。** 一笔一笔收拾的时候，每一下都等一整个来回太熬人，
  所以这一处做的是**乐观更新**：点下去先改这一行的样子，请求失败了再回滚并说明原因。
  页头那两个数（共几条、其中几条已隐藏）由服务端算准了交回来——「全表还隐藏着几笔」
  客户端算不出来。哪一档排不排得下这一行也由服务端说了算（`keep`），不然在「只看
  隐藏」那一档里还原一笔，它还会赖在列表上不走。

**隐藏一笔会把它所在的合并组散掉。** 净额是几笔凑出来的一个数，抽掉其中一笔，
「几笔」和「多少」就再也对不上——那正是这个项目最想避免的那种静默错位。与其在
两者之间挑一个报出来，不如让那几笔原样各算各的；还原之后想再合起来，重新勾一次
就行。（自动检测也不会拿隐藏的行去凑组合。）

## 翻账

交易记录页是拿来一路翻着看的，所以：

- **不分页，滚到底自动接上下一段。** 一次给一段（200 条），往下滑到底就自动取更多，
  位置不动。会丢掉上下文的「第 3 页」这种翻法，不如让列表自己往下长。
  （早先没有 JS，只能点一下才给下一段；现在界面是个 SPA，那个限制不在了。
  底下的按钮仍然留着——键盘用户和「不想它自己长出来」的人都还能用。）
- **筛的是起止日期，默认看整本账。** 打开这一页就是全部记录——这一页的用途是
  翻账，默认缩在某个月的话，想看上一段得先改一次日期。想看某一段就把起止日期填上，
  清空就是回到全部（空着 = 那一端不限，两个都空 = 整个账本）。
  **汇总页不一样，那边默认「当月 1 号到今天」**：那一页问的是「最近花得怎么样」。
  两边的默认值各按各的用途定，不是漏改了一边。
  原先只有一个「月份」框，跨月的那一段——比如「上月 20 号到今天」——筛不出来。
- **筛选栏能收起来。** 有筛选就默认收起，生效的条件写在标题那一行（平时就是
  「2026-10-01 至 2026-10-17」）。不写出来的话，收起来之后这一屏看着就跟全部记录
  一模一样，而合计数又是按筛过的算的。
- **「操作」那一列在最后，而且钉住不动。** 表格横向滚起来的时候，被推出可视区的正是
  最后那几列；`sticky right-0` 让它滚到哪儿都在手边（见 `TransactionsPage.tsx` 里的
  `STICKY`）。钉住是为了窄屏和长摘要——「对方」「说明」两格的字有多长是记账的人
  写的，指望不上。
- **「对方」和「说明」各占一列，但表格是 `table-fixed`。** 两列平分剩下的宽度，
  长文字在格子里折行（最多两行 / 三行，点进详情页看全文），不会把表格撑出容器——
  窄到手机那么宽也一样，钉住的操作列才不会盖住正文。
  日期和钟点因此上下排：并排放的话日期那一列要宽出一截，挤的正是正文。
- **每行开头都有一个分类 emoji**，没分类的给 ❓（名字挂在 tooltip 上，未分类就写
  「未分类」）。位置固定，扫一列就认得出大类；空着反而让两列的字忽左忽右。

### 一笔的详细信息

点列表上的日期、或者「对方」「说明」那两格，进的是这一笔的详细信息页
（`/transactions/<id>`，只读）。列表是拿来扫的，这一页是拿来对账的，所以把它摊开：

- 时间、收支，以及**换算到显示币种之后的金额**（主金额）；原始金额与币种以小字
  跟在旁边，并在下面的明细里保留一行「原金额」；
- 交易对方、对方账号、说明、备注、支付方式、状态；
- 分类三份**分开列**：账单自带的、你手改的、现在算的（前两份各自留着，改错了能对回去）；
- 账户、订单号、商户单号、来自哪次导入（能点进去看那次导入）、在哪个合并组；
- 最底下是**账单原文**整行：文件里那一行的每一列，原样列出来。

空着的字段照样留一行横杠——字段凭空不见，比留个横杠更难解释。手动记的一笔没有
账单原文可摊，就写「手动记的一笔」。

这一页顶上就三个动作：改、隐藏 / 显示、删除。隐藏和还原在这一页上按，回的还是这一页。

## 合并（净额）

一笔支出和它之后跟着来的收款，往往是同一件事的两头。账本里那几笔单独看都对，
合起来是错的，合并就是把它们还原成一件事、按**净额**算。两种形状：

**AA / 拼单。** 帮别人垫了 £120，朋友先后转账还了 £40、£40。账本里于是有
「支出 120 + 收入 40 + 收入 40」三笔——单独看都对，合起来是错的：**真实的消费只有
£40**，汇总页却两头虚高（支出虚增 80，收入凭空多出 80）。规则一句话：
**一笔支出，加上它之后一小段时间里的若干笔等额转入，每个人头分到的份额跟每笔转入
都对得上，就是一次 AA。**

**收支平衡。** −£4.49 之后五小时 +£4.49。钱原封不动回来了——退款、转出去又转回来、
自己两个账户之间倒一下——真实收支是 0，账本里却是「支出 4.49 + 收入 4.49」，
两头各虚增一笔。规则：**一笔支出，之后一笔跟它等额的收入**。只认一笔对一笔：
几笔凑成一笔支出的那种形状（−£120 后面跟着三个 +£40）跟「四个人吃饭、三位朋友各还
一份」在数学上完全分不开，按平衡判得 0、按 AA 判得 £30，两个都不算错，所以干脆不猜，
留给手动合并。

合并之后，这几笔在页面上显示成一行，金额是**净额**（AA 那例是 −£40，收支平衡是 0
——净额 0 的行按中性算，不进合计）。汇总页、图表一律按净额算。**原始记录一个字都没改**，
跟汇率一样是「看的时候算」的：取消合并，几笔就原样回到列表里。

两条规则共用同一套参数，默认 12 小时窗口、每笔允许差 £0.5（`settings.toml` 里可改），
各自有一个开关。

几处刻意的选择：

- **净额影响所有统计**，不只是列表好看。只在列表合并的话，汇总页依然是「收入虚增
  80」的那个错数。
- **收款得看起来像「钱回来了」**（对方/说明/分类/交易类型里命中「转账、红包、收款、
  还款、代付、AA、拼单、分账、transfer、repay、split」之一）才参与自动合并——两条规则
  共用这一道过滤。它挡的是**形状巧合**：薪水入账 £3000 和一笔 £6000 的消费，正好
  构成「两人各半」的形状；一笔日常消费和一笔恰好同额的入账，也能构成「收支平衡」的
  形状，纯按数学判都会合上。漏掉的下场轻得多——手动勾两下就合上了。
  `keywords` 写成空列表就是关掉这道过滤，只按数学判。
- **容差以绝对额为准，小份额再压一道比例上限。** 差多少钱跟消费大小本来就不成比例：
  一份 £40 的份额差三毛很常见，¥200 的份额也差不多是这个数，所以默认 ±£0.5。
  但金额很小时绝对额会失控——£1.12 分成两人，份额只有 £0.56，±£0.5 相当于九成，
  一笔 £0.12 的收款也会被凑成 AA。所以每笔偏差还要不超过份额的 25%；大额时这个
  上限远大于绝对容差，等于不起作用。真误合了就取消合并，那一笔支出之后不会再
  自动合上；嫌松就把 `tolerance` 调小。
- **中性行不参与。** 它本来就不计收支，并进来改变不了净额，只会让人以为算错了。
- **跨币种可以合**（刷卡那笔在 Monzo，朋友从微信还钱）：每笔先换算到显示币种，
  再算净额。所以改汇率会让历史合并的净额跟着变——这也是「看的时候算」的一部分。
- **但没配汇率的币种合不了**，手动合会直接报错、自动检测会跳过它。换算碰上没汇率的
  币种是原样返回的（全应用都这样：没汇率的币种单独成组，绝不按 1:1 混算），
  硬合就会得到一个标着显示币种、其实是原币种数字的净额——不报错，数还是错的。
  这条**每次读页面时都重新判**：已经合好的组要是后来把某个币种的汇率删了，它会
  当场失效、退回成各笔单独显示（合并组页上会写明白缺谁的汇率），而不是继续显示
  一个硬凑的净额。把汇率补回来，它就自己生效。
- **一组归到组内最早那一笔的月份**，也就是消费那个月。跨月的 AA 不会因为还款晚到
  一天就换个算进别的月。
- **一笔只能属于一个组**（数据库上的唯一约束）。不然净额会被算两遍，而且不报错。
  两条规则也是**一起判、一起分**的：分头判的话，一笔收款被两条规则同时看中时，
  两边都以为自己拿得到，落库时后一组撞上唯一约束被静默跳过——同一份数据，这一轮
  少合一组、下一轮补上，页面在两次刷新之间会变。真撞上了让「收支平衡」先拿：
  一笔收款跟支出分毫不差，比「它正好是某笔支出的一半」更像钱绕了一圈回来。
- **取消过的组合不会自己回来**：手动取消时记一笔「这笔支出别再自动合」，
  之后无论导入还是重新扫描都不会再合上它。想合就手动勾。

几处入口：

| 想干什么 | 在哪儿 |
| --- | --- |
| 看有哪些组合并了、展开看成员、改标题/分类、取消合并 | 「合并组」页（交易记录页有入口） |
| 自己挑几笔合起来 | 交易记录页勾选 → 「合并所选」 |
| 给以前记好的账补上检测 | 合并组页的「重新扫描整个账本」 |
| 关掉自动合并 / 改窗口、容差、关键词 | 设置页的「合并」一节（或 `settings.toml` 的 `[merge]` 段） |

```toml
# ~/.local/share/bill/settings.toml
[merge]
enabled = true          # 导入后自动检测并合并
balanced = true         # 收支平衡的那两笔（净额 0）也合上
window_hours = 12       # 收款落在支出之后多久算同一次
tolerance = 0.5         # 每笔收款与它该对上的数允许差多少（显示币种）
keywords = ["转账", "红包", "收款", "还款", "代付", "AA", "拼单", "分账", "transfer", "repay", "split"]
```

`tolerance` 对两条规则是一个意思：AA 里是「每笔收款与人均份额」的差额，
收支平衡里是「那笔收入与支出」的差额。

改完刷新页面就生效。**自动合并是猜出来的，所以每一组都看得见、都能取消**：
合并组页逐组列出净额和成员，合出来不对劲时先看设置页上那几个参数。

## 利息按月汇总（收入）

余额宝这类每日收益，账单原文是「不计收支」，一天一条会把交易记录淹没。开启后，
说明里命中关键词的**中性**记录会按自然月合成一条**收入**：

- 只认中性记录；「自动转入」无论关键词怎么配都不参与（硬排除）。
- 分组身份是「账户 + 对方 + 自然月 + 币种」，同一个月只出一条。
- 合成行按收入计入汇总、图表、分类和账户统计；原始记录的方向、金额、账单原文
  一个字不改，随时能取消合并。
- 金额**先按原币把一个月加起来，再一次性换算**。逐笔换算会把 12 笔 ¥0.01
  舍成 0，月度汇总不会。
- 只有一笔的月份先不建组，等第二笔到来再合。
- 新导入的收益会追加进已有月份，不会另起一条；手改过的组标题/分类保留。
- 取消后按「账户 + 对方 + 月 + 币种」记住，之后补导入也不会自己回来。
- 缺汇率的币种合不了；补上汇率后自动生效。
- 区间筛选按组内最早一笔的日期决定整月是否进入结果——只选一个月的后半段时，
  整月收益可能不在结果里。这是按月汇总的固有代价。

```toml
# ~/.local/share/bill/settings.toml
[merge]
rollup = true
rollup_keywords = ["收益发放"]   # 留空 = 不匹配任何记录
```

设置页的「利息按月汇总」一节对应这两项。给以前的账补上，去「合并组」页点
「重新扫描整个账本」。

## 加一家银行

复制模板，改成你银行的实际列名：

```bash
cp src/bill/data/profiles/bank_generic_example.toml \
   ~/.local/share/bill/profiles/我的银行.toml
```

然后只改 `[profile]` 的 `name` / `title` 和 `[columns]` 里的列名，**不用碰 Python**。
不确定列名是什么，就先把文件传上去，列映射页会把实际读到的表头列出来。

`/profiles` 页列出所有已加载的配置和它们当前认哪些列名（**不在主导航里**：
入口在设置页和导入页上，认不出格式时预览页也会指过去）。

配置里有三处是银行流水的主要差异点：

```toml
[columns]
date   = ["交易日期", "记账日期"]   # 候选列名按顺序试，谁先出现用谁
amount = ["交易金额", "发生额"]

# 日期和时间分成两列时（Monzo 就是这样），额外映射一个 time，
# 会跟 date 拼起来再解析。
time   = ["Time"]

# 账单有币种列就映射上，没有就用 [profile] 里的 currency（默认 CNY）。
currency = ["Currency"]

# 这份账单的时间是哪个时区（IANA 名字）。留空 = 已经是显示时区，不换算。
# timezone 是 [profile] 段的键，不是 [columns] 的：
#   [profile]
#   timezone = "Europe/London"

[parse]
# 怎么判断这笔是收还是支，三选一：
#   "direction_column" —— 金额恒正，另有一列写「收入/支出」，要配 [values]
#   "negative_is_out"  —— 单列带正负号，负数是支出（储蓄卡常见）
#   "negative_is_in"   —— 负数反而是收入（信用卡账单常见）
sign_convention = "negative_is_out"

# 对方名称去掉空白、忽略大小写后做子串匹配，命中就记中性。
# 用来兜住「转给自己另一张卡」「购汇」这类内部转账——它们常常只有一边在文件里。
neutral_counterparties = ["沈宏阳", "HONGYANG SHEN"]
# 交易名称等于这些值时记中性（退款不是收入）。
neutral_descriptions = ["网上快捷退款"]

# 「收/支」列等于这些值的行，导入后直接隐藏（仍入库、仍参与去重）。
# 支付宝的内置配置就是这样处理「不计收支」的。留空 = 不自动隐藏。
[values]
hidden = ["不计收支"]

[dedup]
id_column = ["流水号"]   # 没有就留空，会自动改用内容指纹去重

# 账单用中文写币种时，映射成 ISO 代码；中文键必须加引号，TOML 裸键只认 ASCII。
[values.currency]
"英镑" = "GBP"
"人民币" = "CNY"
```

PDF 账单（内置的中国银行就是这样）由读取层用 pdfplumber 抽表格，配置里写
`[profile].format = "pdf"`。加密 PDF 会先试文件名去掉扩展名作密码；文件改名后
解不开，报错会说清楚。扫描件（图片版）没有文字层，导不进来。

收支分成两列的银行（借记/贷记、借方/贷方），改用 `amount_in` / `amount_out`：

```toml
[columns]
amount_in  = ["贷方发生额"]
amount_out = ["借方发生额"]
```

`[cleanup].footer_patterns` 里的正则负责丢掉末尾的汇总行。另外：

- **`min_columns` 别往上调**。它只是兜住零星的窄行，定高了会把「末尾几列为空」的
  合法行一起吃掉。汇总行由 `footer_patterns` 负责，不靠它。
- 用户目录里同名的配置会**覆盖**内置配置。想改内置的支付宝配置，写一份同名文件
  到自己目录里就行。

## 数据在哪

| 内容 | 路径 |
| --- | --- |
| 账本数据库 | `~/.local/share/bill/bill.db` |
| 设置（配色、汇率、时区、大额阈值、合并） | `~/.local/share/bill/settings.toml` |
| 设置页覆盖前的原文件（只留一份） | `~/.local/share/bill/settings.toml.bak` |
| 登录账号、密码哈希与会话密钥 | `~/.local/share/bill/auth.toml` |
| 你自己的列映射 | `~/.local/share/bill/profiles/*.toml` |

`BILL_DATA_DIR` 可以整体改到别处，`BILL_DB` 单独指定数据库位置。
备份就是拷 `bill.db` 这一个文件（连同 `-wal` / `-shm` 一起拷更稳）。

删掉某次导入会把那次带进来的记录**一起删掉**——导入历史页上可以这么反悔。
那些记录要是正好在某组合并组里，整组会跟着解散：留下一个少了一笔、净额已经被悄悄
改掉的半截组，比直接散开难解释得多。

## 这一版没做的

- **自动归类**。分类先是照用账单文件里自带的「交易分类」那一列，再不然就是你手改的
  （交易记录页上单改或批量改）。没有做「关键词 → 分类」那层规则去猜：微信账单没有
  分类列，所以它默认全归在「未分类」，改起来是勾选一次的事。
- **跨来源对账**。同一笔钱从支付宝和银行各导一次会被记成两条，不会自动抵消。
  合并解决的是另一件事（一笔支出和它后面那几笔收款），不是对账。
- **手动合并里的「部分分摊」**。合并只按净额算，没有「这笔我出七成」那种写法。
- **按对方或摘要豁免大额**。大额只按金额一个维度判定，没有「工资永远不算大额」
  这样的规则——工资超了阈值就得把 `in` 调大。
- **逐条把某笔大额算回合计**。现在能改金额了，把那一笔的金额改成低于阈值就行，
  只是没有「这笔算回合计」这样一个专门开关。单笔「不算数」有隐藏那一档。
- **多用户**。登录就一组账号密码，账本也就一份：分不出「这笔是谁记的」，也没法让两个人
  各看各的。要多人合用，得先给记录加上归属，那是另一件事。

## 开发

```bash
uv run pytest
```

测试样本（GBK 的支付宝账单、微信 xlsx、各类银行流水）都在 `tests/factories.py` 里
用代码现造，不往仓库里塞二进制——真实样本到了，改一行参数就能对上。

想用真实账单做回归测试，把它们放到 `tests/fixtures/real/`（已在 `.gitignore` 里）再跑
`uv run pytest -m real`。真实账单含个人信息，**不要提交**。

### 代码结构

```
src/bill/                     后端：只出 JSON
├── web.py         应用装配（装接口、发前端产物、挡没登录的人）
├── api.py         JSON 接口：取数那一半 + 改库那一半
├── dashboard.py   首页的预测、平均、趋势：拿几个取数结果拼出来（不写 SQL）
├── params.py      地址栏/表单参数 → 取数用的几个值（接口与页面共用同一套语义）
├── auth.py        登录：账号名、密码哈希、会话密钥、失败计数
├── themes.py      配色的**名字与标签**（颜色在 frontend/src/theme/theme.json）
├── settings.py    设置的读取、校验、表单读写、落盘
├── ingest.py      上传 → 预览 → 确认，以及内存暂存
├── importer.py    表 + 配置 → 交易（纯函数，没有 IO）
├── profiles.py    列映射配置的加载、校验、探测打分
├── readers.py     字节 → 表（编码、分隔符、ZIP、Excel、PDF）
├── db.py          连接、建表、迁移
├── repo.py        所有 SQL 都收在这里（含合并后的净额口径）
├── groups.py      合并的检测规则（纯函数，输入是已换算的金额）
├── entry.py       记一笔 / 改一笔的表单读写（不碰 Flask）
├── money.py       金额解析，一律整数「分」
├── dates.py       日期解析
├── dedup.py       去重键
└── data/profiles/ 内置列映射（支付宝 / 微信 / 中国银行 / 银行模板）

frontend/                     前端：React + TypeScript（Vite 构建）
├── src/api/       接口客户端与类型（金额字段一律整数）
├── src/components/ 通用组件（表格、按钮、图表…）
├── src/pages/     一页一个
├── src/theme/     theme.json：四套配色的唯一来源
└── scripts/       从 theme.json 生成主题的 CSS 变量块
```

合并的净额写在 `repo.py` 的 `_effective_cte()` 里：没入组的交易原样保留，每个组换成
一行净额（先按当前汇率换算，再相加）。**统计查询一律从它取数，写入和去重一律看
真实的 `transactions` 表**——序列号、唯一索引、内容指纹都长在那上面。

`api.py` 那一层只做「取数 + 序列化」，一行 SQL 都不写：接口和界面看到的必须是同一
份数，唯一的办法就是它们取的是同一处。**金额一律整数最小单位，JSON 里绝不出现
浮点**（`tests/api.py` 里有个递归扫描，任何响应里冒出浮点都会红）。
