# 记账

把支付宝、微信、银行导出的账单文件导进来，自动记录成结构化的收支。
本地 Web 应用，数据存在本机 SQLite 里，文件不出这台机器。

界面就四个 tab：**汇总**（也就是首页）、交易记录、导入账单、设置。

## 跑起来

```bash
uv sync
uv run bill
```

默认监听 `0.0.0.0:8001`（所有网卡）。本机开 <http://127.0.0.1:8001>，
从别的机器就用这台机器的 IP，例如 <http://10.0.0.5:8001>。

## 登录

```bash
uv run bill --set-password              # 交互式，问两遍
echo '……' | uv run bill --set-password  # 脚本 / 管道里这么给
```

设完之后每一页都要先过密码（`/healthz` 和样式表除外），**改完不用重启**——跟设置
一样每次请求现读。密码存在 `~/.local/share/bill/auth.toml`，里面是 scrypt 加盐哈希，
不是明文；会话密钥也在那份文件里，所以重启服务不会把你从浏览器里踢出去。

**没设密码 = 不设防**，跟以前一样谁都能看。这种状态会在每个页面顶上挂一条提示，
不会悄没声地过去；要主动关掉登录，把 `auth.toml` 删掉即可。

一个密码、一个人，没有多用户也没有「找回密码」——忘了就再跑一次 `--set-password`，
旧的当场作废。同一个来源连错 5 次会歇 60 秒；**歇的是「猜」，不是人**——这段时间里
输对密码照样进得来（一个人用的账本只有这一个密码，被别人拿错密码堵在门外比被多猜
几次糟得多）。计数在内存里，重启服务就清零。

> ⚠️ 走的是明文 HTTP：密码和会话 cookie 在有嗅探的网络上都是明摆着的。这道防线
> 挡的是「能连上 8001 端口的人」里那些顺手点进来的人，不是网线那头的人。真要隔着
> 不受信任的网络用，还是靠防火墙兜住，或者 `HOST=127.0.0.1` + SSH 隧道。

`HOST` / `PORT` 可以覆盖监听地址，`FLASK_DEBUG=1` 开调试模式。

## 设置页

下面那些 `.toml` 里的东西，绝大部分在「设置」页上就能改：配色、显示币种与汇率、
时区、大额阈值、合并的几个参数。保存写的是你自己的那份配置
（`~/.local/share/bill/settings.toml`），**整份重写**；写之前会把原来的内容留一份
`settings.toml.bak`（只留一次，不会被后来的保存顶掉）。手改文件仍然照旧有效。

### 配色

四套，在设置页上点一下即换：

| 名字 | 说明 |
| --- | --- |
| `dark` | 深色（默认） |
| `light` | 浅色 |
| `dark-teal` | 深色 · 青橙 |
| `light-teal` | 浅色 · 青橙 |

四套各有自己的收入 / 支出色。这两色**同时**是表格里那些数字的颜色和图表里柱子的
颜色，所以挑的时候有两个约束，缺一不可：

- **分得开**。红绿色盲下的 OKLab 色差 ≥ 8（四套分别是 19.2 / 20.3 / 10.1 / 9.4）。
- **读得清**。当正文用，对各自的表面 ≥ 4.5:1。原来那对绿 / 红是 2.1，等于红绿色盲
  完全分不出收入和支出。

配色表在 `src/bill/themes.py`，`style.css` 里每个主题一个 `:root[data-theme=…]`
块。**两处必须逐项一致**：图是服务端画的内联 SVG（拿不到 CSS 变量），所以同一组
颜色在两处各有一份。`tests/test_charts.py` 逐项比对，并且自己把对比度和色差算一遍——
多一个少一个变量都会挂。

### 界面里不写实现说明

一个约定：**页面上只放数据、控件和必要的警告**，不写「金额已按 1 GBP = 8.9 CNY
换算」「时间均已换算到 Europe/London」这类说明，也不写「为什么这样设计」的辩解。
它们读起来像提交说明，而且真正要在意的人看这一页就够了。口径（阈值多少、汇率多少、
窗口多长）在设置页上是**控件本身**，不在页面顶部另起一段话。
`tests/test_settings.py` 里有条用例拦着这件事。

## 支持的账单

| 来源 | 格式 | 说明 |
| --- | --- | --- |
| 支付宝 | 明细 CSV（GBK 编码），或包含它的 ZIP | 前面有账户说明、末尾有汇总，都会自动跳过 |
| 微信 | 账单 XLSX | 金额是纯数字，`/` 表示不计收支 |
| Monzo | 导出 CSV | 日期和时间分两列，金额带正负号，币种是英镑 |
| 银行 | CSV / XLSX，**列映射可配置** | 见下面「加一家银行」 |

拿到新的账单文件直接传上去就行。认不出格式时预览页会把文件开头的**原始内容**摊出来，
并指到列映射那一页——那儿列着刚读到的**真实表头**，照着改配置即可。

## 币种与汇率

账本里可以同时有人民币和英镑（比如微信 + Monzo）。所有金额都按汇率**换算成同一种
币种**显示和统计，默认是英镑：

```toml
# ~/.local/share/bill/settings.toml
[currency]
display = "GBP"
rates = { CNY = 8.9 }     # 1 GBP = 8.9 CNY，也就是人民币金额 ÷ 8.9 = 英镑金额
```

改完刷新页面就生效，不用重启。这几项在**设置页**上就能改；想手改文件的话，内置的
那份在 `src/bill/data/settings.toml`，复制到上面的路径就行。

**没配汇率的币种不会被合并。** 它们仍按原币种单独成组列出来（汇总页上各是一个
带币种标题的块）。把没有汇率的币种按 1:1 混进合计会得到一个不报错的错数——
那比报错危险得多，所以宁可多一个分块，也不写那句话去解释。

原始金额和币种一直留在库里（`amount_cents` / `currency`），换算是查询时做的，
所以改汇率随时可以重算，不会把历史数据改坏。金额一律存整数最小单位
（人民币的「分」、英镑的便士），跟币种无关。

**不做历史汇率**：用的是你现在设的这一个数，不是每笔交易发生当天的汇率。

## 时区

账单给的时间都是**当地的墙上时钟**，不带偏移量，而且各来源还不一样：

| 来源 | 时间是哪个时区的 |
| --- | --- |
| 微信 / 支付宝 | UTC+8（微信账单第一页自己就这么写着） |
| Monzo | 英国本地时间（会随夏令时变） |

账本统一换算到一个显示时区，默认英国：

```toml
# ~/.local/share/bill/settings.toml
timezone = "Europe/London"   # 必须写在文件最上面，不能写在 [currency] 之后
```

换算在**导入时**做一次，原始的那串时间一直留在 `raw_json` 里随时能对回去。

不换算会怎样：北京时间 `11-01 02:00` 的一笔，按英国时间其实是 `10-31 18:00`，
不换算就会被算进 11 月——**而这不会报任何错**。同理，一天之内两种来源的先后顺序
也会错位。

用的必须是 IANA 名字（`Europe/London`）而不是固定偏移量，因为英国一年里会
夏令时切换两次；写错名字会在读设置时就报错，不会拖到导入。（设置页上那一格同理，
填错了当场告诉你。）

自己加的银行配置默认**不换算**（当作已经是显示时区）；只有当那份账单来自别的
时区时，才需要在 `[profile].timezone` 里声明。

## 大额交易

买台 iPad 的 −£1000、或者爸爸给的 +£5000，混在日常收支里会把「累计支出」「累计收入」
抬到一个不反映真实水平的数。所以超过阈值的单笔**不进合计**，但仍**照常留在账本里**，
在汇总页最底部单独列一块（标题里带着条数）。

```toml
# ~/.local/share/bill/settings.toml
[large]
out = 500     # 单笔支出 ≥ 500 就算大额
in  = 2000    # 单笔收入 ≥ 2000 才算；0 表示这一侧不启用
```

这两项在设置页上直接填，改完点保存即可。

阈值是**显示币种的主单位**，不是人民币，也不是英镑——跟着 `[currency] display` 走。
所以同一个「500」在 GBP 账本下是 £500，在 CNY 账本下就是 ¥500。**人民币账本下这两个
默认值多半要往上调**：¥2,000 只相当于约 £225，一笔正常工资就会被当成大额剔掉。

只对**换算得到显示币种**的记录生效。没配汇率的币种比不了（拿英镑的阈值去比人民币的
数没有意义），所以那几组里一笔都不会被判成大额——跟「没配汇率就不合并」是同一个
道理，都是宁可少做也不给一个不报错的错数。

判断是**查询时**做的，跟汇率换算一样：改完阈值刷新页面就重算，库里不加列、不改数据。
今天觉得 £1000 算大额，明年想改成 £1500，改个数就行，历史数据不会被动过。

几处刻意的选择：

- **收入和支出分开两个阈值，而且默认都开着**。两者尺度本来就不同，共用一个数会让
  收入那一侧形同虚设（工资通常就超过一般的支出阈值）。但收入侧默认开着是有代价的：
  **月薪一旦超过 `in`，就会被整个剔出「累计收入」**。所以汇总页底部那一块带着条数
  （「不计入合计的大额（2 笔）」），设置页上那两个数就是当前生效的阈值——数字可以
  被改小，但不该是悄悄被改小的。发现剔错了，把 `in` 调大，或者写 `0` 关掉那一侧。
  刻意**不**在合计数旁边再写一段话解释它：那一段话既长又像变更说明，而需要它的人
  看设置页就够了。真觉得对不上账时，数一数底部那几笔的条数。
- **条数照实计数**，不跟着剔除。大额行确实在账本里，只是不参与金额合计——中性行
  早就是这个待遇了。所以「记录条数」减去「金额合计覆盖的条数」是正常的。
- **交易记录页上它们在金额旁标一个「大额」标签**，金额照原样显示。抹成 0 反而更糟：
  那一笔确实发生了，页面上却写成没发生。列表页那一行里没有「计入合计」这一列，
  这个标签就是唯一的交代。
- **导入预览页不套阈值**。那两格是「新增收入/支出」，回答的是「这次写进去多少」，
  不是「账本合计多少」。
- **不分页也不截断**汇总页的那份清单。大额本来就是稀有事件，截断反而会造出「说明里
  写着 N 笔、列表里只有几笔」这种对不上账的情形。真把阈值设得极低，那长长的列表
  本身也是明摆着的。

## 图表

汇总页每个币种配两幅图：**每月收支**（分组柱状，收入与支出共用一根零轴）和
**支出构成**（横向条形，按分类排前 10）。

纯服务端渲染成内联 SVG——不用 JS、不引图表库。这个应用本来零前端依赖，图表不该
成为第一个。**每个数值在页面下方的表格里都能查到**，图只负责让人一眼看出趋势和
构成，不是唯一的读数途径。

几处刻意的选择：

- **收入与支出共用一根纵轴**。做成「收入向上、支出向下」的双向柱等于两套刻度，
  一边大一边小时会互相骗人。
- **支出构成只有一种颜色**，不按金额深浅上色——那等于把柱子长度再编码一遍，
  白白占掉唯一的颜色通道。分类只有一个时不出图，给一句话（微信账单没有分类列，
  支出全归「未分类」，会走到这种情况；手动改过分类之后就不会了）。
- **配色跟着主题走**，四套主题各有自己的收入 / 支出色（见「设置页 · 配色」）。
  这几个色都跑过色盲校验，也都能当正文颜色用。图表是服务端画的 SVG，取的是
  `themes.py`；`style.css` 里那份是给表格和标签用的，两边必须一致，有测试逐项比对。
- 悬停显示具体金额用的是 SVG 原生的 `<title>`，不需要 JS。数值另有表格可查，
  所以提示只是锦上添花。
- 每月收支只画**最近 12 个月**——月份再多柱子就细得看不出差别，更早的月份在
  下面的表里仍然查得到。图上还给每组最高的那根直接标了值。
- 图下方是一行合计（合计收入/支出/结余/月均支出，或分类的合计与占比），
  这部分用 HTML 排，不画进 SVG：文字交给浏览器排版比在坐标系里手摆位置稳。
- 手机上图表**横向滚动**而不是等比缩小：缩到 375px 宽时字号只剩五六个像素，
  与其看不清不如保持可读的尺寸让用户滑一下——表格本来就是这个做法。

## 导入流程

传文件 → **预览确认** → 入库。预览这一步是关键：

- 认成了哪份配置、匹配度多少，可以手动改选并**就地重新解析，不用重传文件**
- 会新增几条、有几条跟库里重复、有几条是中性收支、几条解析不了
- 解析出问题的行会连同**原始内容**列出来，方便你拿去改配置
- **确认之前不会写进账本**，所以格式认错了也不会污染数据

预览只存在内存里，进程重启或放置超过 30 分钟会失效（已入库的数据不受影响）。

## 收支的三个方向

不是「收入 / 支出」两个，而是三个：

- `收入`、`支出` —— 计入合计
- `中性` —— 支付宝的「不计收支」、微信的「/」。转账、还款、退款都归这里

中性行**照常入库**（金额留着、列表里看得见），但不计入任何收支合计。
数据库里用一个视图把这件事固化下来，所以统计查询不可能「忘了排除中性行」。

汇总页上它们**只剩一行灰字**（「另有 N 笔中性记录未计入合计」，带个入口点进交易记录
逐笔看，那一页也能按「中性」筛）。早先它们在汇总页上是一块独立的表（条数 + 金额
合计），跟收入、支出、结余并排——那等于把「不计收支」的东西也摆成一张账，读起来像
「有一块账没算进去」。收入、支出、结余三个数里没有它们，才是这件事的全部意思：
把「转给自己另一张卡」算成支出，等于凭空造出一笔消费。

## 重复导入不会翻倍

记账是长期的，账户区间重叠是常态——这个月导了 1/1–1/31，下个月导 1/15–2/28，
中间两周是重合的。去重就是为这件事做的。

分两层：

1. **唯一订单号**：支付宝的「交易订单号」、微信的「交易单号」，有就用它。最可靠。
2. **内容指纹**：没有订单号时（多数银行流水），对「时间 + 方向 + 金额 + 对方」取哈希。

内容指纹**刻意不含摘要和备注**。不少银行每次导出都会把日期、网点拼进摘要
（`消费` 变成 `消费 某超市 2026-01-10`），把它们算进指纹的话，同一笔钱在区间重叠的
两次导出里就成了两笔，长期按月导会越滚越多。备注本来就给人改的，同理。

兜底的两道保险：

- 区间跟历史导入有重叠时，预览页会**明说**跟哪一次重叠了。
- 去重键认不出来、但账本里已有「同一天 + 同方向 + 同金额」的记录时，标成
  **疑似重复**并列出来让你过目。这种情况多半是连对方名都被改写了。

有一处刻意做得不那么「聪明」：**同一份文件里出现两笔一模一样的消费，会被当成两笔真交易
都保留下来**（第二条带个 `#2` 后缀），而不是合并成一条。同一分钟内买两次一样的东西是
真实存在的，静默合并比多存一条糟得多。同理，退款行复用了原订单号也不会被吞掉。

去重按**账户**隔离。同一笔钱从支付宝和从银行流水各导一次不会被自动合并——那属于对账问题，
靠弱内容匹配去自动合并风险更大。

「疑似重复」的行**照常导入**，不自动丢弃：丢真账的代价比多一条大，判断留给你。

## 手改与手动记账

导入只是起点，账总有要动手的地方。交易记录页上：

- 每行末尾的「操作」列上有「改 / 隐藏 / 删」，页头有「记一笔」（临时用现金付的、
  别人代付的都靠它）
- 勾选几笔，可以**一起改分类**，也可以**合并成一组**（见下一节）

几处刻意的选择：

- **手动记的一笔不属于任何账单文件。** 它 `import_id` 留空，落在单独的「手动记账」
  账户里，去重键是个随机值。所以它不参与账单去重——同一天手滑提交两次就是两条，
  跟真买了两次一样。理由和「同一份文件里两笔一模一样的消费都保留」是同一条：
  静默吞掉一笔真账，比多存一条糟得多。
- **手改的分类不会盖掉账单原文。** 账单自带的分类（支付宝的「交易分类」、Monzo 的
  Category）留在 `source_category`，你改的写在另一列 `category`，没改过就回落到
  原文。所以改错了、想对回原样都还有得对，跟「原始金额和币种一直留在库里」一个道理。
- **编辑绝不重算去重键和内容指纹。** 这是全项目最容易踩、踩了还不报错的一处：
  那两个字段是「这条记录的身份」，重算之后重新导入同一份账单时比不中指纹，
  同一笔钱会被**再插一遍**——账翻倍，屏幕上什么都不说。所以账户、来源分类、
  订单号这些也一律不给改：要改分类，改的是上面那个 `category`。
- **改一笔不影响它所在的合并组**——手动合的是你自己勾的，自动合的被改了金额/方向/
  币种/时间会散开（见下一节）。
- **秒不会被悄悄抹掉。** 表单里的时间精确到秒，点一次保存改的是你动过的那部分；
  只到分钟的话，改个备注就把账单里的秒数改了。
- 手机上勾选之后操作条在表格下面，**没有「全选本页」**：批量操作那一块不带 JS，
  与其写一半的交互，不如让人手勾。

### 「隐藏」不是删除

删了就没了；隐藏是把这一笔从账本的口径里摘出去，随时能还原。所以：

- **隐藏之后它不进任何合计**——汇总、图表、大额、币种清单里都没有它。库里那一行
  照旧在，原始金额、币种、去重键、内容指纹一个字不动，**所以重新导入同一份账单也
  不会又插一遍**（跟编辑一样，去重那块的东西谁都别碰）。
- **交易记录页上它照旧列出来，灰字**，勾选列里挂着「隐」，末尾的「操作」列里是「显示」，
  点一下还原。金额照原样写着，不抹成 0——那一笔确实花出去了，页面上写成 0
  才是假数；跟大额一样，靠标记交代它不算数。
- **它连勾选框都没有。** 它不进合计，也就不该能被合进一组。想只挑出这些行，筛选栏
  里有一档「已隐藏」。
- **隐藏不盖「已改」那枚标签。** 那个标签说的是分类手改过；隐藏改的是算不算数，
  跟内容改没改是两件事，混用一个标记会让人以为记录被改过。
- **按「隐藏」不会重载整页。** 一笔一笔收拾的时候，每一下都等一整个来回太熬人，
  所以这一处用了一小段脚本：提交照旧发给那个表单的地址，回来只把这一行、页头那行字
  和「还有几条」换掉。**它是一层加法**——脚本没跑（关掉了，或者请求不成）就退回原来
  那条 303 回列表的路，功能一样在。这也是全站唯一的一段 `<script>`。

**隐藏一笔会把它所在的合并组散掉。** 净额是几笔凑出来的一个数，抽掉其中一笔，
「几笔」和「多少」就再也对不上——那正是这个项目最想避免的那种静默错位。与其在
两者之间挑一个报出来，不如让那几笔原样各算各的；还原之后想再合起来，重新勾一次
就行。（自动检测也不会拿隐藏的行去凑组合。）

### 一笔的详细信息

点列表上的日期、或者「对方 / 说明」那一格，进的是这一笔的详细信息页
（`/transactions/<id>`，只读）。列表是拿来扫的，这一页是拿来对账的，所以把它摊开：

- 时间、收支、**原始金额与币种**，以及换算到显示币种之后的金额；
- 交易对方、对方账号、说明、备注、支付方式、状态；
- 分类三份**分开列**：账单自带的、你手改的、现在算的（前两份各自留着，改错了能对回去）；
- 账户、订单号、商户单号、来自哪次导入（能点进去看那次导入）、在哪个合并组；
- 最底下是**账单原文**整行：文件里那一行的每一列，原样列出来。

空着的字段照样留一行横杠——字段凭空不见，比留个横杠更难解释。手动记的一笔没有
账单原文可摊，就写「手动记的一笔」。

这一页顶上就三个动作：改、隐藏 / 显示、删除。隐藏和还原在这一页上按，回的还是这一页。

## 合并（净额）

一笔支出和它之后跟着来的收款，往往是同一件事的两头。账本里那几笔单独看都对，
合起来是错的，合并就是把它们还原成一件事、按**净额**算。两种形状：

**AA / 拼单。** 帮别人垫了 £120，朋友先后转账还了 £40、£40。账本里于是有
「支出 120 + 收入 40 + 收入 40」三笔——单独看都对，合起来是错的：**真实的消费只有
£40**，汇总页却两头虚高（支出虚增 80，收入凭空多出 80）。规则一句话：
**一笔支出，加上它之后一小段时间里的若干笔等额转入，每个人头分到的份额跟每笔转入
都对得上，就是一次 AA。**

**收支平衡。** −£4.49 之后五小时 +£4.49。钱原封不动回来了——退款、转出去又转回来、
自己两个账户之间倒一下——真实收支是 0，账本里却是「支出 4.49 + 收入 4.49」，
两头各虚增一笔。规则：**一笔支出，之后一笔跟它等额的收入**。只认一笔对一笔：
几笔凑成一笔支出的那种形状（−£120 后面跟着三个 +£40）跟「四个人吃饭、三位朋友各还
一份」在数学上完全分不开，按平衡判得 0、按 AA 判得 £30，两个都不算错，所以干脆不猜，
留给手动合并。

合并之后，这几笔在页面上显示成一行，金额是**净额**（AA 那例是 −£40，收支平衡是 0
——净额 0 的行按中性算，不进合计）。汇总页、图表一律按净额算。**原始记录一个字都没改**，
跟汇率一样是「看的时候算」的：取消合并，几笔就原样回到列表里。

两条规则共用同一套参数，默认 12 小时窗口、每笔允许差 £0.5（`settings.toml` 里可改），
各自有一个开关。

几处刻意的选择：

- **净额影响所有统计**，不只是列表好看。只在列表合并的话，汇总页依然是「收入虚增
  80」的那个错数。
- **收款得看起来像「钱回来了」**（对方/说明/分类里命中「转账、红包、收款、还款、
  代付、AA、拼单、分账、transfer、repay、split」之一）才参与自动合并——两条规则
  共用这一道过滤。它挡的是**形状巧合**：薪水入账 £3000 和一笔 £6000 的消费，正好
  构成「两人各半」的形状；一笔日常消费和一笔恰好同额的入账，也能构成「收支平衡」的
  形状，纯按数学判都会合上。漏掉的下场轻得多——手动勾两下就合上了。
  `keywords` 写成空列表就是关掉这道过滤，只按数学判。
- **容差是绝对额，不是百分比。** 差多少钱跟消费大小本来就不成比例：一份 £40 的份额
  差三毛很常见，¥200 的份额也差不多是这个数，按比例卡反而两头都不对。
  代价得说清楚：**小额支出会显得宽松**——£6.7 三个人分，每人 £2.23，±£0.5 相当于两成。
  真误合了就取消合并，那一笔支出之后不会再自动合上；嫌松就把 `tolerance` 调小。
- **中性行不参与。** 它本来就不计收支，并进来改变不了净额，只会让人以为算错了。
- **跨币种可以合**（刷卡那笔在 Monzo，朋友从微信还钱）：每笔先换算到显示币种，
  再算净额。所以改汇率会让历史合并的净额跟着变——这也是「看的时候算」的一部分。
- **但没配汇率的币种合不了**，手动合会直接报错、自动检测会跳过它。换算碰上没汇率的
  币种是原样返回的（全应用都这样：没汇率的币种单独成组，绝不按 1:1 混算），
  硬合就会得到一个标着显示币种、其实是原币种数字的净额——不报错，数还是错的。
  这条**每次读页面时都重新判**：已经合好的组要是后来把某个币种的汇率删了，它会
  当场失效、退回成各笔单独显示（合并组页上会写明白缺谁的汇率），而不是继续显示
  一个硬凑的净额。把汇率补回来，它就自己生效。
- **一组归到组内最早那一笔的月份**，也就是消费那个月。跨月的 AA 不会因为还款晚到
  一天就换个算进别的月。
- **一笔只能属于一个组**（数据库上的唯一约束）。不然净额会被算两遍，而且不报错。
  两条规则也是**一起判、一起分**的：分头判的话，一笔收款被两条规则同时看中时，
  两边都以为自己拿得到，落库时后一组撞上唯一约束被静默跳过——同一份数据，这一轮
  少合一组、下一轮补上，页面在两次刷新之间会变。真撞上了让「收支平衡」先拿：
  一笔收款跟支出分毫不差，比「它正好是某笔支出的一半」更像钱绕了一圈回来。
- **取消过的组合不会自己回来**：手动取消时记一笔「这笔支出别再自动合」，
  之后无论导入还是重新扫描都不会再合上它。想合就手动勾。

几处入口：

| 想干什么 | 在哪儿 |
| --- | --- |
| 看有哪些组合并了、展开看成员、改标题/分类、取消合并 | 「合并组」页（交易记录页有入口） |
| 自己挑几笔合起来 | 交易记录页勾选 → 「合并所选」 |
| 给以前记好的账补上检测 | 合并组页的「重新扫描整个账本」 |
| 关掉自动合并 / 改窗口、容差、关键词 | 设置页的「合并」一节（或 `settings.toml` 的 `[merge]` 段） |

```toml
# ~/.local/share/bill/settings.toml
[merge]
enabled = true          # 导入后自动检测并合并
balanced = true         # 收支平衡的那两笔（净额 0）也合上
window_hours = 12       # 收款落在支出之后多久算同一次
tolerance = 0.5         # 每笔收款与它该对上的数允许差多少（显示币种）
keywords = ["转账", "红包", "收款", "还款", "代付", "AA", "拼单", "分账", "transfer", "repay", "split"]
```

`tolerance` 对两条规则是一个意思：AA 里是「每笔收款与人均份额」的差额，
收支平衡里是「那笔收入与支出」的差额。

改完刷新页面就生效。**自动合并是猜出来的，所以每一组都看得见、都能取消**：
合并组页逐组列出净额和成员，合出来不对劲时先看设置页上那几个参数。

## 加一家银行

复制模板，改成你银行的实际列名：

```bash
cp src/bill/data/profiles/bank_generic_example.toml \
   ~/.local/share/bill/profiles/我的银行.toml
```

然后只改 `[profile]` 的 `name` / `title` 和 `[columns]` 里的列名，**不用碰 Python**。
不确定列名是什么，就先把文件传上去，列映射页会把实际读到的表头列出来。

`/profiles` 页列出所有已加载的配置和它们当前认哪些列名（不在主导航里，
认不出格式时预览页会给出链接）。

配置里有三处是银行流水的主要差异点：

```toml
[columns]
date   = ["交易日期", "记账日期"]   # 候选列名按顺序试，谁先出现用谁
amount = ["交易金额", "发生额"]

# 日期和时间分成两列时（Monzo 就是这样），额外映射一个 time，
# 会跟 date 拼起来再解析。
time   = ["Time"]

# 账单有币种列就映射上，没有就用 [profile] 里的 currency（默认 CNY）。
currency = ["Currency"]

# 这份账单的时间是哪个时区（IANA 名字）。留空 = 已经是显示时区，不换算。
# timezone 是 [profile] 段的键，不是 [columns] 的：
#   [profile]
#   timezone = "Europe/London"

[parse]
# 怎么判断这笔是收还是支，三选一：
#   "direction_column" —— 金额恒正，另有一列写「收入/支出」，要配 [values]
#   "negative_is_out"  —— 单列带正负号，负数是支出（储蓄卡常见）
#   "negative_is_in"   —— 负数反而是收入（信用卡账单常见）
sign_convention = "negative_is_out"

[dedup]
id_column = ["流水号"]   # 没有就留空，会自动改用内容指纹去重
```

收支分成两列的银行（借记/贷记、借方/贷方），改用 `amount_in` / `amount_out`：

```toml
[columns]
amount_in  = ["贷方发生额"]
amount_out = ["借方发生额"]
```

`[cleanup].footer_patterns` 里的正则负责丢掉末尾的汇总行。另外：

- **`min_columns` 别往上调**。它只是兜住零星的窄行，定高了会把「末尾几列为空」的
  合法行一起吃掉。汇总行由 `footer_patterns` 负责，不靠它。
- 用户目录里同名的配置会**覆盖**内置配置。想改内置的支付宝配置，写一份同名文件
  到自己目录里就行。

## 数据在哪

| 内容 | 路径 |
| --- | --- |
| 账本数据库 | `~/.local/share/bill/bill.db` |
| 设置（配色、汇率、时区、大额阈值、合并） | `~/.local/share/bill/settings.toml` |

`BILL_DATA_DIR` 可以整体改到别处，`BILL_DB` 单独指定数据库位置。
备份就是拷 `bill.db` 这一个文件（连同 `-wal` / `-shm` 一起拷更稳）。

删掉某次导入会把那次带进来的记录**一起删掉**——导入历史页上可以这么反悔。
那些记录要是正好在某组合并组里，整组会跟着解散：留下一个少了一笔、净额已经被悄悄
改掉的半截组，比直接散开难解释得多。

## 这一版没做的

- **自动归类**。分类先是照用账单文件里自带的「交易分类」那一列，再不然就是你手改的
  （交易记录页上单改或批量改）。没有做「关键词 → 分类」那层规则去猜：微信账单没有
  分类列，所以它默认全归在「未分类」，改起来是勾选一次的事。
- **跨来源对账**。同一笔钱从支付宝和银行各导一次会被记成两条，不会自动抵消。
  合并解决的是另一件事（一笔支出和它后面那几笔收款），不是对账。
- **手动合并里的「部分分摊」**。合并只按净额算，没有「这笔我出七成」那种写法。
- **按对方或摘要豁免大额**。大额只按金额一个维度判定，没有「工资永远不算大额」
  这样的规则——工资超了阈值就得把 `in` 调大。
- **逐条把某笔大额算回合计**。现在能改金额了，把那一笔的金额改成低于阈值就行，
  只是没有「这笔算回合计」这样一个专门开关。单笔「不算数」有隐藏那一档。
- **滚到底自动取下一段**。交易记录页是点一下给一段（见「翻账」），不是滚到表底就
  自己长出来——那得再开一个分片接口、再写一段脚本去拉，而现在全站只有「隐藏」
  那一段。
- **多用户**。登录就一个密码，账本也就一份：分不出「这笔是谁记的」，也没法让两个人
  各看各的。要多人合用，得先给记录加上归属，那是另一件事。
